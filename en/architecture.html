Architecture

Current map

Repositories, runtimes, modules, invariants, and tensions: the project as it exists today, not as it would be convenient to narrate it.

I. Principles

Structural principles

Frida no longer rests on a single codebase or a single surface. Its architecture has thickened into two complementary runtimes and a documentation site. The principles below are what keep those forms intellectually and technically coherent.

Principle Description
Explicit modular decomposition Responsibilities are named and separated as far as possible: orchestration, memory, summaries, retrieval, dialogic regime, arbitration, documents, LLM, local tools.
Two runtimes, one programme Frida_V4 and FridaDev do not implement exactly the same thing, but they work on the same core problems: dialogic continuity, memory, judgment, and observability.
Distinct memory statuses A trace, a summary, a retrieved snippet, an imposed document, or an operator log do not have the same status. To confuse them is to lose the discipline of the system.
Fail-open and visible degraded modes A failed module must not disguise itself as silent success. Fall-backs, interruptions, and runtime limits need to remain explicit.
Observability first Logs, audits, admin surfaces, and persistence states are part of the architecture, not an optional afterthought.
Documentation aligned with the code The public site and documents should not advertise a fictional system. They should reflect current state, evidence, and missing pieces.

II. Organisation

Layers and modules

Frida is no longer a single diagram pinned to a wall. Today the project exists as a native runtime, a web runtime, and a public site. Unity does not come from identical implementation, but from the persistence of shared questions and contracts.

III. Invariants

System invariants

The invariants below describe less an abstract ideal than a common line of conduct across the repositories.

  1. Public documentation must remain aligned with the real state of code, tests, and audits.
  2. The orchestrator should stay lighter than the semantic modules it connects: it routes and assembles, it should not absorb all the system's meaning.
  3. Trace, summary, retrieved snippet, injected document, and operator log keep distinct statuses.
  4. A dialogic or hermeneutic signal is never evidence by itself. It can orient a processing regime; it does not replace a factual basis.
  5. Canonical persistence and streaming contracts matter as much as model calls: without them, dialogue has no reliable memory.
  6. Local or agentic capabilities must remain bounded by execution profiles, logs, and explicit guardrails.
  7. The two runtimes may diverge technically, but they should remain describable in a compatible conceptual vocabulary.
  8. Module evaluation cannot stop at attractive output quality; it must also inspect refusals, revisions, interruptions, and degraded modes.

IV. Tensions and open questions

Problems currently under exploration

The project remains active precisely because these questions are not settled.

  • Evaluating dialogic regime control. How should the real effect of a module such as M6 on coherence, non-overinterpretation, or response stability be measured?
  • Runtime convergence. How far should Frida_V4 and FridaDev converge without being artificially forced into one mould?
  • Memory and documents. How should memory retrieval, summaries, and imposed documents be articulated without collapsing their hierarchy or operator legibility?
  • Voice, local tools, security. How can agentic and multimodal capabilities be enriched without undoing requirements of control, auditability, and least surprise?
  • Honest scientific publication. How can some modules be turned into publishable papers without overselling results or flattening the code's current limitations?
