Frida

A bilingual project, two runtimes, one public documentation site: Frida explores a form of dialogic AI that is more memory-aware, more situated, and more accountable.

The project

One project, two application repositories, one site repository

Frida is now organised around two public application repositories and one site repository. Frida_V4 carries a native macOS runtime in Swift, modular and oriented toward dialogue, memory, documents, voice, and local orchestration. FridaDev carries a Python/Flask web runtime with browser chat, memory, a hermeneutic branch, a public streaming contract, and observability surfaces. frida-ai is the repository of the bilingual public site that documents this work and hosts its public-facing texts.

The project is therefore no longer only a theoretical intuition. It is a real software programme composed of contracts, modules, tests, architecture documents, and operator-facing surfaces. What is being pursued here is not just a more fluent assistant, but a more disciplined way of conducting dialogue with an LLM: better turn grounding, better memory boundaries, clearer uncertainty, and more legible degraded modes.

The philosophical question remains, but it is now handled as an engineering programme. How should continuity through time be organised? How should traces, summaries, retrieved snippets, and user-injected documents be distinguished? How can a dialogic or hermeneutic signal influence the response regime without standing in for evidence? How can the whole system remain intelligible to an operator?

Frida does not claim to have solved machine understanding. It builds concrete paths for working on it: structured memory, arbitration, dialogic regime control, document injection, local tools, voice transcription, speech synthesis, and explicit persistence or streaming contracts.

Frida is less an abstract promise than an active research architecture held together by code, documentation, and critical revision.

Research areas

01

Native modular runtime

Decomposing dialogue into named and testable modules: orchestration, present-state, memory, summaries, retrieval, dialogic regime, arbitration, documents, LLM, and local agent loop.

02

Web runtime and conversation contract

Maintaining a robust web pipeline: session, memory, hermeneutic branch, public streaming, frontend rehydration, memory admin, and observability.

03

Memory, arbitration, dialogic regime

Working on continuity, trace selection, evidence bounding, and dialogic conduct without confusing style, judgment, and truth.

04

Voice, documents, and observability

Integrating Whisper, TTS, imposed documents, and operator logs into one research programme rather than letting them drift into isolated features.

Architecture — overview

An architecture already distributed across several forms

The core of Frida is not a manifesto page but a set of effective runtime chains. In Frida_V4, the trajectory runs from the M0 orchestrator to memory modules, retrieval, M6 Stimmung, M7 Arbiter, M8 Documents, M9 LLM, local agentic execution, and Whisper/TTS integrations. In FridaDev, the public pipeline articulates session handling, augmented system context, memory branching, hermeneutic branching, a public streaming contract, canonical persistence, and admin surfaces.

The public site now has a precise role: to reflect this real state. Not a finished system, but a modular, observable, documented research platform concrete enough to produce audits, papers, evaluations, and technically situated hypotheses.
